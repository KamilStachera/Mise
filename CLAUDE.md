# Pichci (repo: CukBuk) — developer guide

Pichci (formerly "Mise") is a multi-household, Polish-language AI-assisted cookbook: recipes, a
quantity-based pantry, shopping list, weekly plan, cook log — all exported as an
AI-readable `./context/<householdId>` folder and writable through a REST API / MCP server.
See `README.md` for the user-facing story.

**Language rule:** UI text and all data content are Polish; code, API contracts,
commit messages and docs stay English. Polish labels live in
`frontend/src/lib/labels.ts`; sorting uses `pl-PL` collation.

## Run / verify

```bash
docker compose up -d --build    # web :8080, API :5080/api (Swagger /api/swagger)
```

Migrations auto-apply on API boot. For end-to-end verification (Playwright over
the real UI, API probes, context-file checks) follow `.claude/skills/verify/SKILL.md`.

**Access control:** writes (and private reads) need a Google session of a household
member, a personal API key (`X-Api-Key: pk_…`), or `AUTH_DEV_BYPASS=true` in `.env`
(the local-dev default from `.env.example`; acts as the first person, `X-Person` may
pick anyone, which is how you test several households locally). Anonymous = read-only
on `PUBLIC_HOUSEHOLD_ID`, if set. With bypass off the UI hides
all mutation controls for anonymous visitors — remember this when driving the
app with Playwright.

**The Docker volumes hold the user's real data (~60 recipes, live pantry).
Never `docker compose down -v` or reseed without explicit permission.** Seeding:
recipes/profile only on a brand-new DB; the pantry catalog reseeds whenever
`PantryItems` is empty.

Frontend dev loop: `docker compose up db api` then `cd frontend && npm run dev`
(Vite :5173 proxies `/api` → :5080).

**Host .NET SDK may not match `global.json` (9.0.304).** Build, test and add
migrations in the SDK image instead (Git Bash; `MSYS_NO_PATHCONV=1` keeps the
paths intact):

```bash
MSYS_NO_PATHCONV=1 docker run --rm -v "E:/Repos/CukBuk:/src" -v pichci-nuget:/root/.nuget/packages \
  -w /src mcr.microsoft.com/dotnet/sdk:9.0 sh -c "dotnet test backend.tests"
# migrations: -w /src/backend … sh -c "dotnet tool install -g dotnet-ef --version '9.*' \
#   && export PATH=\$PATH:/root/.dotnet/tools && dotnet ef migrations add <Name>"
```

Without Docker: a newer host SDK (10.x) builds and tests the net9.0 projects when run from
a folder *outside* the repo (so `global.json` doesn't apply), e.g.
`dotnet test E:/Repos/CukBuk/backend.tests/Mise.Api.Tests.csproj`; for migrations use a
local `dotnet-ef` 9.x tool manifest in that folder plus `--project <repo>/backend/Mise.Api.csproj`.

## Layout

- `backend/` — .NET 9 minimal APIs. `Features/<X>Endpoints.cs` (one file per
  resource, grouped under `/api`), `Domain/Entities.cs` (single file, XML-doc
  comments carry the invariants — read it first), `Services/` (matcher, parsers,
  context export), `Data/` (EF Core, migrations, seed).
- `frontend/` — React + Vite + TS. `pages/` map 1:1 to nav routes, `api/client.ts`
  (fetch + DTO types) and `api/hooks.ts` (react-query), inline styles with CSS
  variables from `theme/tokens.css` (no CSS framework, no icon set).
  - Look (2026-10 redesign): paper background, 1px ink rules instead of cards,
    Newsreader titles / Schibsted Grotesk UI / JetBrains Mono numbers — use
    `var(--serif|--sans|--mono)`, never literal family names.
  - Build pages from `components/ui.tsx` (PageTitle, Button, Chip, UnderlineTabs,
    Segmented, Toggle, StatStrip, SearchField, Eyebrow, SectionHead, Sheet…).
    Editors and pickers open in a `Sheet` (bottom sheet on phones, dialog on
    desktop), not inline cards.
  - Shell: `Sidebar` (desktop) / `TabBar` (≤700px, `useIsMobile`); `<main>` is
    the scroll container. Phone pages that pin an action bar position it
    `fixed` at `TAB_BAR_HEIGHT` + safe area; `/recipe/*` hides the tab bar.
  - React gotcha: after `border: 0` on a `<button>`, never pass
    `borderBottom: undefined` — React writes an empty value and the UA button
    border comes back. Use `0`.
- `mcp/` — stdio MCP server proxying the API (`mcp/src/index.ts`). `dist/` is
  gitignored: after any tool-schema change run `cd mcp && npm run build`.
  `MISE_PERSON` sets the `X-Person` header (whose diary the tools touch).
- `sous/` — the in-app Sous runner (`AI_PROVIDER=codex`): Codex SDK signed in with
  the ChatGPT plan (`sous-codex` volume), cwd `/context` read-only, the MCP server
  bundled in its image. `CodexChatProvider` sends one turn per message; the Codex
  thread id rides on the AI `ChatMessage.MetadataJson`. Its prompts are
  `AgentDocs.SousInstructions`/`SousTurn`. Rebuild `sous` after MCP tool changes.
- `context/` — **generated output, gitignored, never hand-edit.** Regenerated by
  `ContextExportService` after every successful write. All agent-facing text
  (AGENTS.md/CLAUDE.md/api.md, slash commands, Profile-screen snippets) has a
  single source: `backend/Services/AgentDocs.cs` — edit there. When you change
  an endpoint or contract, update `AgentDocs.ApiMd` and the MCP tool schemas in
  the same change.

## Invariants that bite

- **Households are tenants.** Every household-owned entity implements `IHouseholdOwned`
  (`HouseholdId`); `MiseDbContext` hides other households with global query filters
  (children — ingredients, steps, images, equipment, contributions, program days —
  filter through their parent) and its `SaveChanges` stamps new rows from
  `TenantContext` and throws `TenantViolationException` on cross-household writes.
  A new entity that belongs to a household must implement `IHouseholdOwned` (and
  `IPersonOwned` if per person) — then filtering and stamping are automatic. A fresh
  scope sees nothing (fail closed): request scopes get their tenant from
  `ApiAccessMiddleware`; boot code and hosted services must call
  `TenantContext.UseSystem()` (sees all, must set `HouseholdId` on inserts) or
  `UseHousehold(id)`. Lookups that run before the tenant is known (people by email,
  API keys, HC tokens) use `IgnoreQueryFilters()` — keep that the exception.
  `Exercise.HouseholdId` null = shared catalog, set = an agent's custom exercise.
- **Who is calling** is resolved once per request by `People.ResolveAsync` into the
  scoped `Caller` (kind, own person, acting person, household, admin) and the tenant.
  Order: dev bypass → personal key (`ApiKeys`, SHA-256) → system key (`MISE_API_KEY`,
  sous only, must send `X-Person`) → Google email → anonymous. `X-Person` is honoured
  only within the caller's household. A Google account with no person is `Unlinked`:
  only `/api/auth` and `/api/onboarding` work (403 `needsOnboarding` elsewhere).
  Invites (`InviteCode`, hashed, single use, soft-revoked via `RevokedAt`, rate-limited
  redeem) and new-household provisioning (`HouseholdProvisioner`: per-household seed with an
  **empty** cooking profile — never the owner's tastes — + private starter copy with own photo
  files) live in `Features/HouseholdEndpoints.cs`. New people get the „Pierwsze kroki” checklist
  (`Services/FirstSteps.cs`, `/api/household/first-steps`, card on the library): steps tick
  from real data, never by hand; `Person.FirstStepsDismissedAt` hides it, and everyone who
  existed before it (incl. household-1 bootstrap imports) starts dismissed.
- **Roles, admins, blocking.** `Person.Role` is `Owner`/`Member`: only owners (or admins)
  invite, rename the household or other people and change roles (`Caller.IsOwner`); a
  household always keeps an owner (`HouseholdEndpoints.SetRoleAsync`). Admin =
  `Person.IsAdmin` or `ADMIN_EMAILS` (the lock-out fallback; never demotable/blockable in
  the panel), Google session only — API keys never carry admin rights. A blocked person
  or household resolves to `CallerKind.Blocked` (403 `blocked` everywhere but
  `/api/auth`, keys and Sous included). Nothing is hard-deleted: block, unlink (email →
  null, keys revoked), revoke. The admin panel API is `Features/AdminEndpoints.cs` — the
  only feature code that reads across households (`IgnoreQueryFilters()` on purpose).
  **Every admin/owner mutation adds an `AuditEvent`** via the scoped `Audit` service
  (saved with the same `SaveChanges`); keep that when adding admin actions.
- **All /api access flows through `Services/ApiAccessMiddleware.cs`** — a
  middleware, not a group filter, so it also covers the `/api/images` static
  files and `/api/swagger`. It resolves the caller first, then: privileged → through;
  `/api/images` and `/api/exercises` GETs are open; other anonymous GETs only reach
  the public household (`PUBLIC_HOUSEHOLD_ID`) and never the private prefixes
  (`/api/chat`, diary, body, activity, training, household, keys, admin,
  `/api/context/status|connect`, swagger). `MISE_API_KEY` unset ⇒ the system key is
  disabled (fail closed). The frontend derives read-only mode from
  `GET /api/auth/me` (`useAuth()` in `api/hooks.ts`) — wrap any new write UI in
  `canEdit`; `needsOnboarding` swaps the whole app for `pages/Onboarding.tsx`.
  Context exports are per household (`ContextExportService.Directory` =
  `{ContextDir}/{householdId}`); Sous gets `household` and works in that folder.
- **Pantry = ingredient catalog.** `Quantity: 0` means "known, not at home" and
  the item stays listed. Status In/Low/Out is **derived**
  (`Features/Dtos.cs` → `Mapping.StatusOf`), never stored or settable.
- **Match-only vs create.** `POST /pantry/adjust` (deltas) and `/pantry/bulk`
  (absolute) only match existing items — unmatched names come back in
  `notInCatalog`, nothing is created. Creation is only `POST /pantry`
  (unit required; fuzzy duplicate → 409). Two matcher thresholds
  (`Services/IngredientMatcher.cs`): 85 (`ExactishScore`, bidirectional) for
  quantity mutations, 60 for recipe-ingredient→pantry linking. Don't loosen the
  85 — it's what stops "Chipsy paprykowe" from adding to "Papryka".
- **Supplies ("Dom") is a third, separate list.** `SupplyItem` is name + guessed
  category only — no quantity, no unit, no pantry link, no relation to
  `ShoppingItem`. `SupplyFavorite` is the add-count tally behind the "hot items"
  chips and **deliberately outlives the items**: `clear-checked` hard-deletes rows,
  so deleting the tally alongside them would destroy the only history the ranking
  has. Ranking lives in `Services/SupplyService.cs` (pinned → decayed count →
  `Pl.Comparer`); seeded staples carry `AddCount = 0` so they sort last and get
  displaced by real use. Both lists share the `/shopping` route
  (`pages/Shopping.tsx` is a shell; `/shopping/dom` selects the household tab).
- **The plan is also the food diary.** `PlanEntry` is one calendar item, several per
  slot (no unique (Date, Slot) any more; `snack` slot added). Planned → eaten is
  `EatenAt`; eating a recipe entry **snapshots** its kcal/macros (totals, not per
  portion) — never recompute eaten history from the recipe. A `Cook` is one pot spread
  over days: the cook-day entry plus `IsLeftover` entries; shopping counts only the cook
  day, scaled to `Cook.Portions` (`PlanShoppingService.NeedsShopping`). Rules live in
  `Services/DiaryService.cs` / `BodyService.cs`. `/api/diary` and `/api/body` are
  private even for reads; anonymous `GET /plan` hides snacks, typed food and eaten
  state (`Mapping.PublicView`). Spec + design: `docs/weight-loss/`.
- **The diary is per person; the kitchen is per household.** `Person` rows live in the DB
  (one Google email = one person = one household; emails stored lower-case). `PersonScope`
  = `Caller.Acting` (the `X-Person` pick within the household, else the caller's own
  person) scopes `PlanEntry`, `Cook`, `FoodFavorite`, body profile, weights, energy,
  workouts, `HealthSync`, `Catering` and training. A personal key acts as its owner;
  anonymous visitors act as the public household's first person. Shopping, pending-cook
  and the plan.md export stay household-wide — don't scope them by person.
  `DIARY_PEOPLE`/`AUTH_ALLOWED_EMAILS` are imported into household 1 **once** (marked by
  a `system.legacy-import` audit event, so an unlink survives reboots); `ADMIN_EMAILS` is
  applied every boot (missing admins join household 1, `IsAdmin` set) —
  `People.ImportLegacyConfigAsync`. `Person.LastSeenAt` / key `LastUsedAt` are touched by
  the middleware at most every 5 min.
  Frontend: private query keys carry `usePerson().id`; the header comes from `api/person.ts`.
- **Catering is materialized, not virtual.** `CateringService.EnsureAsync` (run by
  `GET /plan`, `/body/budget`, `/body/progress`) writes one eaten `IsCatering` entry per
  delivery day up to today and advances `MaterializedThrough` — a deleted day never comes
  back and new numbers never rewrite past days.
- **Band/scale sync = `POST /api/hc/{token}`** (HC Webhook app on her phone →
  Health Connect data). It is the one write that bypasses `ApiAccessMiddleware`; the
  endpoint checks the URL token (`HealthSync`, rotatable). Raw energy intervals are
  upserted on (Kind, Start, End) — the app re-sends updated records. Band workouts
  take their kcal from Active samples inside their window (never add them twice);
  manual workouts add their own. A manual weigh-in beats the scale; the scale keeps
  the day's earliest reading; a reading >5 kg off the person's last month is the other
  person on the shared scale and is dropped. Each person has their own token. Days are Polish days: the api container runs
  `TZ=Europe/Warsaw` (docker-compose) — `DateTime.Today` depends on it.
- **Recipe import (links, PDFs) only reads.** `Services/Import/`: `/api/import/url` and
  `/api/import/documents` hand agents the source (schema.org JSON-LD → microdata → page text;
  PDF text per page in `ImportDocument`, 14-day scratch rows); the agent normalizes and saves
  through `POST /recipes` like any recipe. **Every server-side fetch of a user-supplied URL
  goes through `SafeWebFetcher`** — it refuses non-public IPs in the connect callback (covers
  redirects and DNS rebinding); the API sits on the home LAN.
- **Shopping list is fully decoupled from the pantry.** Nothing appears or
  disappears automatically; rows come from recipe add-missing, manual entry, or
  agents. There is no sync-from-pantry code — don't reintroduce it.
- **`PUT /recipes/{id}` is full-replace.** Omitting `dishType`/`cuisine`/
  `usesAirFryer` clears them (then air-fryer falls back to the text heuristic in
  `Services/AirFryer.cs`, which needs `Steps` loaded — keep the `Include`s).
- **Recipe photos:** gallery table `RecipeImages`; `Recipe.ImagePath` marks the
  default (newest upload becomes default). Files live in the `mise-images`
  volume (`ImagesDir` config), timestamped names = cache busting. IFormFile
  minimal-API endpoints need `.DisableAntiforgery()`. Uploads over 1 MB are stored as
  WebP (≤ 2048 px, q85; `RecipeImageStore.SaveAsync`) unless WebP isn't smaller or the
  file won't decode — then the upload is kept byte for byte. Existing files aren't touched.
- **Ingredient amounts:** display string `Quantity` + structured
  `AmountValue`/`AmountUnit` (parsed by `Services/QuantityParser.cs`; refuses
  "garść"/"łyżki"). Structured amounts drive quantity-aware "missing" checks and
  post-cook deductions; unparseable ones fall back to presence-based.
- **Dates in the frontend:** always parse `YYYY-MM-DD` with
  `lib/dates.ts` (`new Date('YYYY-MM-DD')` is UTC midnight and shifts the day).
- **Training catalog (`Exercise`) is shared and public to read** (`/api/exercises`);
  per-person training data (`TrainingProfile`, `TrainingProgram` → `ProgramDay` →
  `ProgramExercise`) lives under `/api/training`, private even for reads and scoped to
  `PersonScope` on every lookup by id. Spec: `docs/training/features.md`. Code:
  `Services/Training/`, `Features/ExerciseEndpoints.cs`, `Features/TrainingEndpoints.cs`,
  `Features/TrainingDtos.cs`, `pages/training/`, `components/training/`, `api/training.ts`.
  - Programs: week *n* = n-th calendar week from the Monday of `StartDate`, a day sits at
    (Week, Weekday 0 = Monday), unique per program, never before `StartDate`
    (`ProgramSchedule`, `TrainingRules`). One active program per person — `ActivateAsync`
    archives the old one in its own save first, because of the partial unique index; the
    full-replace PUT deletes old days before inserting new ones (same unique keys), in a
    transaction.
  - Validation lives in `TrainingRules` and names the day ("Tydzień 2, wtorek: …") so an
    agent can fix one spot; follow-along day videos also go through `YouTubeVerifier`.
  - Templates (`TrainingTemplates`, `POST /training/programs/template`) build a plan without AI
    from the questionnaire — curated free-exercise-db staples per slot, then a muscle search,
    within the person's kit (empty home kit = bodyweight only; no bar exercises at home). They
    emit an ordinary `TrainingProgramInput`, so they go through the same validation/activation.
  - `ProgramExercise.Exercise` is `Restrict` on delete — hide catalog exercises, don't
    delete them.
  - The catalog is seeded from vendored free-exercise-db JSON (embedded resource,
    pinned `ExerciseImport.UpstreamSha`). `ExerciseImport` runs every boot and **only
    inserts missing `SourceId`s** — never update rows there, or agent enrichment is lost.
  - Enum tokens are kebab-case on the wire (`middle-back`, `body-only`; `ExerciseTokens`);
    muscle lists are `text[]` of enum names.
  - **Every `youtubeId` write goes through `YouTubeVerifier` (oEmbed)** — agents must not
    be able to store invented ids. `ExerciseCatalog.Prepare` validates without mutating;
    the video is verified before the patch is applied.
  - **Background describer** (`ExerciseEnrichmentWorker` → `ExerciseEnrichment`): with
    `AI_PROVIDER=codex` and `EXERCISE_ENRICH` ≠ `off`, it asks GPT through Sous `POST /job`
    (fresh thread, live web search, no MCP, `outputSchema`) for a batch of exercises, then
    validates and saves itself — GPT never writes. Order: active-plan exercises → missing
    text → home kit → easier levels. Never overwrites existing Polish text; unverifiable
    videos are dropped; per-exercise attempts are in memory (max 3 until restart). Steps
    aside for 2 min after any chat message; usage-limit errors pause it 30 min. Saving a
    program calls `EnrichmentState.Kick()`. Tune with `EXERCISE_ENRICH_INTERVAL` (s) /
    `EXERCISE_ENRICH_BATCH`; set `EXERCISE_ENRICH=off` on dev machines so they don't spend
    the ChatGPT plan on the local DB.
  - Photos are fetched from GitHub on demand (`ExerciseImages`, strict path regex), cached
    as WebP under `{ImagesDir}/exercises-v1/`. Resize code is shared with recipe cards in
    `Services/ImageResizer.cs`.
  - The body map polygons are vendored (MIT) in `components/training/bodyMapData.ts`.

## Adding a feature — the usual checklist

1. Entity/migration (`dotnet ef migrations add X` — see `Data/MiseDbContextFactory.cs`
   for design-time config), endpoint in `Features/`, DTO in `Features/Dtos.cs`.
2. Context export: does `ContextExportService`/`CookbookMarkdownBuilder` need to
   surface it to agents?
3. Agent docs: `AgentDocs.cs` (api.md + AGENTS.md sections), MCP tool in
   `mcp/src/index.ts` + `npm run build`, both READMEs if user-facing.
4. Frontend: `api/client.ts` types → `api/hooks.ts` → page. Polish copy.
5. Verify with the verify skill; clean up any test data you created.
